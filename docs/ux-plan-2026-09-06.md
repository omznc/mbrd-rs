# UX plan — designer feedback, 6 September 2026

Source: a designer who uses FigJam every day. He used the WebAssembly build at
`mbrd.omarzunic.com`. Speed of the web build is out of scope. This plan covers
the behaviour and the feel.

His five points, as written, with a translation:

1. `onboarding mi djeluje malo komplicirano, ne kazen da je al djeluje`
   — the first run *seems* complicated; he does not claim that it is.
2. `scroll na pinch mi je spor` — pinch zoom is slow.
3. `ne mogu ne backspace izbrisat note` — Backspace does not delete a note.
4. `connect opcija gori livo mi je višak kad imaju ove tockice oko svakog
   elementa` — the Connect tool at the top left is surplus, because every card
   already has the small marks around it.
5. `kad san u note mode-u bilo bi dobro da mogu selektirat postojeci note na
   double click, a i pomaknit ga na drag. Cudno mi je da mi opet kreira novi`
   — in Note mode, a double press should select an existing note and a drag
   should move it. A new note instead of that is strange.

## 1 · What the code does now

### 1.1 Note mode (points 5 and 3)

`crates/app/src/board_view.rs`, in the left-press handler, near line 9694:

```rust
match self.tool {
    Tool::Pan => { self.gesture = Gesture::Panning { .. }; return; }
    Tool::Note => { self.add_note_at(world, cx); return; }
    Tool::Connect => { /* hit test, then Gesture::Roping */ }
    Tool::Select => {}
}
```

`Tool::Note` runs no hit test. It puts a note down and returns. Everything that
makes a press mean something else is below this match:

- the eight resize grips;
- the four rope marks (`anchor.rs`);
- the transport controls on a media card;
- the `click_count >= 2` branch, which opens a card or enters a group;
- the hit test itself, which starts `Gesture::Moving`.

So in Note mode a card cannot be selected, moved, resized, joined or opened.
The designer described this exactly.

`add_note_at` (line 3262) also does two more things: it selects the new note,
and it opens the note for typing with the `# note` placeholder selected.

That last part is the whole of point 3. The key handler at line 11218 gives the
press to the open editor first. `editor.rs:433` maps `backspace` to
`self.erase(...)` and answers `Reply::Held`, so the press stops there. The
first Backspace erases the placeholder. Every Backspace after that does
nothing, because the text is already empty.

To leave the editor the designer would press Escape or press somewhere else.
A press somewhere else, in Note mode, makes a second note — and that note opens
for typing as well. So the loop repeats and Backspace never reaches
`Command::Delete`.

`Command::for_key` is correct: `command.rs:829` maps `"delete" | "backspace"`
to `Self::Delete`. The web key bridge is correct too:
`vendor/gpui_ce_web/src/events.rs:573` maps `"Backspace"` to `"backspace"`.
Nothing is wrong with the key. The note was never selectable in the first
place.

One more gap: nothing removes an empty note. `stop_editing` (line 9061) commits
or reverts the text and never asks whether a note that was made a moment ago
still has words in it.

### 1.2 The wheel and the pinch (point 2)

`board_view.rs`, `on_scroll`, near line 10903:

```rust
let (dx, dy) = match event.delta {
    ScrollDelta::Pixels(p) => (f(p.x) / 40.0, f(p.y) / 40.0),
    ScrollDelta::Lines(p)  => (p.x, p.y),
};
if event.modifiers.shift {
    self.camera.nudge((dy + dx) * 40.0, 0.0, &self.viewport);
} else {
    let factor = (1.0 + ZOOM_PER_LINE).powf(dy);   // ZOOM_PER_LINE = 0.12
    self.camera.zoom_by(factor, local, &self.viewport);
}
```

Three separate problems are in these ten lines.

**A pinch is not told apart from a wheel.** `event.modifiers.control` is never
read. The browser sets `ctrlKey` on a trackpad pinch; this is the convention
that every canvas application on the web uses, and the bridge already carries
it (`modifiers_from_wheel_event` in `vendor/gpui_ce_web/src/events.rs`). The
application throws the flag away.

**The rate is far too low for a pinch.** A macOS pinch reports about 1 to 12
pixels for each event. Take 3 pixels: `dy = 3 / 40 = 0.075`, and
`1.12^0.075 ≈ 1.0085`. That is 0.85 % of zoom for each event. A whole pinch of
thirty events gives about 1.3 times. FigJam gives two to four times for the
same hand movement. "Slow" is an understatement.

**A plain two-finger scroll zooms.** FigJam, Figma and Miro all pan on a plain
two-finger scroll. Here it zooms, and `shift` pans sideways only. On a
trackpad there is therefore no way to pan up or down with the fingers at all.
The only ways left are the Pan tool, a drag on empty paper, and the middle
button, which a trackpad does not have.

The sibling JavaScript application already solved this. See
`~/dev/mbrd/web/assets/js/canvas/input.ts`: `classifyWheel()`,
`WHEEL_ZOOM_RATE = 0.0016`, `PINCH_ZOOM_RATE = 0.01`, `WHEEL_MAX_STEP = 400`,
a 200 ms latch for each burst, and `unrail()`.

### 1.3 Connect and the marks (point 4)

`crates/app/src/anchor.rs` draws four marks outside each card: `GAP = 18.0`
from the edge, `REACH = 8.0` of catch area, `DOT = 7.0` across. They appear on
hover. A drag from one starts a rope. Cards below `TOO_SMALL = 30.0` get no
marks at all.

`Tool::Connect` (`tools.rs`) does the same job from a press anywhere on a card:
`nearest_side` picks the side for you, and the tool stays armed so a second
rope needs no second press on the strip.

So the overlap is real. The tool is not useless — it is the only path for a
card under 30 units, and it is faster for a chain of ropes — but a person who
has already found the marks reads the strip entry as a duplicate. Miro has the
same complaint from its own users about its blue dots and its line tool.

The strip is at the **top left**: `tools.rs` renders it with
`.absolute().top(px(10.0)).left(px(10.0))`. `DESIGN-BRIEF.md` says bottom left.
The brief is out of date; the designer read the screen, not the brief.

### 1.4 The first run (point 1)

`crates/app/src/welcome.rs` exists and works. It is four pages:

1. **Appearance** — light or dark, and a theme, with a live preview.
2. **Boards** — a text field for the folder where boards go.
3. **Behaviour** — motion on or off, update checks on or off, then snap and
   grid step for new boards.
4. **Get started** — four doors: new board, open a board, look at the demo,
   take the tour.

The engineering is good. Every control is imported from `settings.rs`, so
nothing is a second implementation. Every press writes through to
`prefs::save`, so Escape never loses an answer. There is no Finish button.

The problem is what it is, not how it is built. Three pages of preferences
stand between a new person and a board. The design brief's own list of needs
put the welcome screen first, and the screen that was built answers the
question "how do you want the application set up?" rather than "what do you
want to make?".

**On the web it is worse, because two of the questions do not apply.**
`welcome.rs` has no `cfg(target_family = "wasm")` anywhere in it.

- Page 2 asks for a **folder path on disk**. A browser has no disk. The page
  even prints "This computer has no home directory, so there is nowhere to put
  a new board until you name a folder."
- Page 3 offers **"Look for new versions"**. `command.rs:957` marks that
  command unavailable on wasm, and the comment there says both update rows are
  "hidden outright in a browser". The welcome screen renders the switch anyway,
  because `command_switch` calls `Command::run` and never asks
  `Command::available`.

A first-time person in a browser is therefore asked, before seeing a board,
where to keep files that are not files, and whether to check for updates that
do not exist. "Seems complicated" is a kind way to put it.

## 2 · The plan

### Stage 1 — Note mode behaves like a tool, not a stamp

**Goal.** In Note mode a press on empty paper makes a note. A press on
anything else does what Select does.

**Change.** Delete the `Tool::Note` arm from the match near line 9694. Put the
note where the press is already known to be on nothing: in the `None` branch of
`match self.hit(world)` near line 9950, after the `rope_at` test and before the
pan-or-marquee split.

```rust
None => {
    if let Some((a, b)) = self.rope_at(world) { self.select_rope(&a, &b, cx); return; }
    if self.tool == Tool::Note { self.add_note_at(world, cx); return; }
    // empty space: plain drag pans, modified drag sweeps
}
```

Because the grips, the marks, the transport controls and the `click_count >= 2`
branch are all above this point, every one of them starts working in Note mode
with no further change. That is the whole of the designer's request: double
press selects, drag moves.

**Keep.** The tool stays armed after a note is put down. That is what FigJam
does with its sticky tool, and it is what makes a row of notes cheap. Keep the
existing carve-out that stops the commit press from stamping a second note.

**Test.** Add to the `board_view` tests:

- a press on empty paper in Note mode adds one item;
- a press on an existing card in Note mode adds nothing and selects that card;
- a drag from an existing card in Note mode moves it;
- a press on a grip in Note mode starts `Gesture::Sizing`;
- a press on a rope mark in Note mode starts `Gesture::Roping`.

**Risk.** Low. One press that used to make a note on top of a card now selects
that card. Nobody wanted the old result.

### Stage 2 — Backspace deletes, and an empty note does not survive

**Goal.** Backspace removes the selected note, and a note that never got words
does not stay on the board.

Stage 1 already fixes the reported symptom: the designer can now leave the
editor, keep the note selected, and press Backspace, which reaches
`Command::Delete`. Two more changes make it hard to get stuck again.

**Change A.** Give `Escape` from a **new, untouched** note the meaning "put it
back". If a note was made by `add_note_at` in this session, and the text on
Escape is the placeholder or empty, remove the note instead of committing it.
Record it as one undo step, so `Ctrl+Z` brings it back.

Add a `born: bool` to the open-edit session so `stop_editing` can tell a new
note from an old one. An old note that a person empties on purpose must stay.

**Change B.** Make the hint line say the way out. `tools.rs:92` reads
`"note — press to put one down; escape for select"`. While a note is open for
typing the status bar shows the edit mode line instead. Change that line to
name both keys, for example `"typing — escape to finish; backspace deletes the
note once you are out"`. Words are cheap and this is the exact confusion.

**Test.**

- Backspace on a selected note that is not open for typing moves it to the bin.
- Backspace inside an open note erases one character and does not delete it.
- Escape on a new note that was never typed into removes it; `Ctrl+Z` returns
  it.
- Escape on an old note that was emptied on purpose keeps the empty note.

**Risk.** Low, but Change A touches undo. Test the undo step by hand as well.

### Stage 3 — The wheel, the pinch and the pan

**Goal.** A pinch zooms at a normal rate. A two-finger scroll pans. A mouse
wheel keeps doing what it does today.

**Change.** Rewrite `on_scroll`. Read `event.modifiers.control` first, then
classify the device, then apply one of two rates.

```rust
/// A trackpad pinch. Matches the rate every other canvas application uses.
const PINCH_ZOOM_RATE: f32 = 0.01;
/// The most one event may zoom, so a coarse wheel cannot jump the camera.
const ZOOM_MAX_STEP: f32 = 400.0;
```

Order of tests:

1. **Position mode over the named card** — unchanged, `dolly_mesh` keeps the
   wheel.
2. **`event.modifiers.control`** — a pinch. `factor = exp(dy_px * PINCH_ZOOM_RATE)`,
   with `dy_px` clamped to `±ZOOM_MAX_STEP`. Use the raw pixels, not the
   value divided by forty.
3. **`event.modifiers.shift`** — pan sideways, as today.
4. **`ScrollDelta::Lines`** — a mouse wheel. Zoom with `ZOOM_PER_LINE`, exactly
   as today. Desktop habit is not disturbed.
5. **`ScrollDelta::Pixels` with no modifier** — a trackpad two-finger scroll.
   **Pan** by `dx` and `dy`, through `camera.nudge`.

Step 5 is the one that changes desktop behaviour, so put it behind a
preference. Add `Setting::TrackpadScroll` to `prefs.rs` with two values, `Pans`
and `Zooms`, and default it to `Pans`. Add the row to the Canvas section of
`settings.rs`. A person who wants the old feel changes one switch.

**Classification is not free.** Some mice report pixels. Port the heuristics
from `~/dev/mbrd/web/assets/js/canvas/input.ts` rather than inventing them:

- a fractional delta means a trackpad;
- any horizontal component means a trackpad;
- `deltaMode == 1` means a wheel;
- latch the answer for the length of a burst, 200 ms of quiet ends the burst.

Put the classifier in its own file, `crates/app/src/wheel.rs`, as a plain
function over a small input struct, so it can be tested without a window.

**Numbers to expect.** At three pixels for each event, the pinch factor goes
from `1.0085` to `exp(0.03) = 1.030`. That is about three and a half times
faster. Tune against FigJam side by side before the number is fixed.

**Test.**

- `wheel.rs`: a stream of fractional deltas classifies as a trackpad; a stream
  of `deltaMode == 1` events classifies as a wheel; one stray fractional event
  inside a wheel burst does not flip the latch.
- `on_scroll`: control plus pixels zooms; pixels alone with the default
  preference pans; lines alone zooms; shift plus anything pans sideways.
- A zoom step is never larger than `ZOOM_MAX_STEP` allows.

**Risk.** Medium, and it is the highest risk in this plan. Wheel behaviour is
muscle memory. The preference is the safety net. Test on a Mac trackpad, a
Windows precision touchpad, a Logitech wheel and a free-spin wheel.

### Stage 4 — Connect stops looking like a duplicate

The designer is right that the two paths overlap, and wrong that the tool is
surplus: it is the only path for a card under `TOO_SMALL = 30.0`, and it is
faster for a chain. So do not remove it. Make each path say what it is for.

**Change A — the marks appear on the selected card, not only on hover.** Miro
does this and it is the cheapest discovery win here. A person who selects a
card sees the four marks at once and never needs the tool.

**Change B — the Connect tool shows every join at once.** While `Tool::Connect`
is armed, draw the marks on every card in view, not only under the pointer.
Then the button means "show me all the places a rope can start", which the
marks alone do not do, and the two stop being the same thing.

**Change C — say it in one line.** `tools.rs:91` reads
`"connect — drag from one card to another; escape for select"`. Change it to
name the alternative, for example
`"connect — drag card to card; the marks on a card do the same one at a time"`.

**Change D — do not remove the tool from the strip yet.** There is no
measurement of use in this application. Removing a mode on one person's first
impression is a guess. Revisit after Change A and Change B, and ask the same
designer again.

**Test.** The marks are drawn for a selected card with no pointer over it. The
marks are drawn for every visible card while Connect is armed. A card under
`TOO_SMALL` still gets no marks and is still reachable with the tool.

**Risk.** Low. Watch the compile-time guard in `anchor.rs`:
`const _: () = assert!(GAP - REACH >= crate::grips::REACH);`. Marks that are
always visible must not steal a press meant for a grip.

### Stage 5 — The first run asks less, and asks it later

**Goal.** A new person reaches a board in one press. The preferences stay,
but they stop being a gate.

**Change A — the web build drops the questions it cannot answer.** This is a
correctness fix, not a matter of taste, and it should ship on its own.

- Drop `Step::Boards` from `Step::ALL` on `target_family = "wasm"`. Filter it
  in `Welcome::open`, next to the filter that already drops `Step::Appearance`.
- Drop the update row from `behaviour()` on wasm, or better, make
  `command_switch` return `None` when `Command::available` is false. The second
  form fixes the class of bug, not one instance of it. `command.rs:957` already
  states the rule; the welcome screen is the one place that ignores it.

After this the web first run is two pages, not four.

**Change B — put the doors first.** Move `Step::Started` to the front. A person
who wants a board presses one door and is gone. A person who wants to set
things up walks the rail. This is a small change to `Step::ALL` and to the
"no Next on the last page" rule, which becomes "no Back on the first page".

An option worth considering instead, if Change B does not test well: drop the
rail on first run altogether. Show the four doors and one quiet line — "You
can set appearance, folders and behaviour in Settings" — and keep the three
preference pages only as `Command::Welcome`, which already reopens the screen
on purpose.

**Change C — rename the pages so they read as offers, not as forms.**
"How it should behave" is a settings heading. On a first run, "Motion and new
boards" says the same and asks less.

**Change D — teach the board, not the preferences.** The four doors already
offer the demo and the tour. Nothing teaches the person who presses "Create a
board" and lands on empty paper. Port the ghost hint cards from
`~/dev/mbrd/web/assets/js/onboarding.ts`: two or three faint shapes on the
empty board that say what to do, and that go away at the first real action.
This is the highest-value item in Stage 5 and the largest. Keep it separate.

**Test.** `welcome.rs` already has tests for the rail and for the doors. Add:

- on wasm, `Welcome::open` yields no `Step::Boards`;
- `command_switch` renders nothing for an unavailable command;
- the first page answers a bare Enter with the first door;
- Escape from the first page still marks the first run done and keeps answers.

**Risk.** Low for Change A. Medium for Change B, because the tests in
`welcome.rs` assert the order of the rail.

## 3 · Problems found while reading, that the designer did not name

1. **A trackpad cannot pan up or down with the fingers.** Covered by Stage 3,
   but note that this is worse than a slow pinch. It is a missing gesture.
2. **`shift` plus wheel pans sideways only.** There is no key that pans up and
   down. Standard practice is that `shift` swaps the axis of a scroll that
   already pans. Stage 3 makes that possible for the first time.
3. **There is no space-to-pan.** Every canvas application has it. `"space"` is
   bound at `board_view.rs:11480` as a step-forward key. A held space that pans
   and returns to the previous tool on release is a small, well-understood
   addition. Add it after Stage 3.
4. **A plain drag on empty paper pans; a modified drag sweeps a selection.**
   That is Miro's rule. FigJam does the opposite. The designer did not complain,
   so leave it. Note it as a known difference and ask him directly.
5. **`command_switch` bypasses `Command::available`.** Named in Stage 5A. It is
   a bug in its own right, and the welcome screen is the only caller today.

were false, and both cost him time. Both are corrected, along with the controls

Correct both before the next round of feedback. Add a line to §4.6 that names

### What Stage 3 actually shipped

Not the latch. `wheel.rs` classifies on the *shape* of one event rather than on
the timing of a burst, because `std::time::Instant` panics on
`wasm32-unknown-unknown` and the web build is the one the designer used. The
rules, in order: `Shift` pans sideways; `control` with pixels zooms, at the
pinch rate under 50 px and at the wheel rate over it; pixels alone pan; lines
zoom. `NOTCH = 50.0` is what keeps `Ctrl` and one detent of a browser mouse
wheel from being read as a pinch of 100 px, which would be `exp(1.0)`.

`Command::ToggleTrackpadPan` and `prefs.trackpad_pans` are the way back, on the
General section of Settings. The first-run screen does not ask about it.

## 6 · Questions for the designer

Ask these with the Stage 1, 2, 5A and 4A build in hand:

1. On a trackpad, should a two-finger scroll pan or zoom? Stage 3 assumes pan.
2. Should a drag on empty paper pan, as Miro does, or sweep a selection, as
   FigJam does?
3. With the marks now on the selected card, is the Connect tool still surplus?
4. On the first run, the doors now come first and the three preference pages
   sit behind them. Is that enough, or would you rather see no screen at all
   and a demo board with hints on it? Stage 5D is the second answer.
5. `wheel.rs` sets the pinch rate at `exp(0.01 · px)`. Put it beside FigJam and
   say whether it is now too fast.
